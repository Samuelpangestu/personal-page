Cross-team regression · Release coordination

One release check for journeys that cross several applications

When each team tests only its own application, the handoffs between applications can go unchecked. I coordinate shared regression checks so a release is judged on the whole journey.

Context
A superapp integration that consolidates 14 standalone applications into one platform, plus 3 new application projects, each built by a squad of 10–20 developers.
Problem
A user journey passes through applications owned by different teams. Each part can pass its own tests while the journey still fails.
My role
Lead a team of 30 QA engineers, coordinate shared regression checks across squads, and run one release review.
Approach
Map each shared journey end to end, include the handoffs between applications in the regression scope, and use contract testing and service virtualization so squads can test in parallel.
Release review
Four questions: scope, test evidence, open risks, and the decision with its reason. The template is below.
Decisions and trade-offs
Two calls shaped the work. First, judge a release on the whole journey, not per application — it costs more coordination across squads, but testing each application alone leaves the handoffs unchecked. Second, let squads test in parallel with contract testing and service virtualization instead of waiting on dependent services — faster, but a virtualised service can drift from the real one, so the contract is the check that keeps it honest.
How I verified it
Shared regression checks run before the release review, and the review itself asks for scope, test evidence, open risks, and the decision with its reason. Once squads could test in parallel, the cross-team integration test cycle went from about two weeks to about three days.
Example
A journey can pass inside one application and still fail at the handoff — for instance, a field the next application expects is missing or formatted differently. The shared checks catch that before the release review.
Outcome
Post-release incidents down 50% through pre-release validation of integrated journeys.

Test automation · Shared foundation

One automation foundation every project builds on

When each project builds its own test framework, the same problems get solved many times and results look different everywhere. I built two shared core libraries and the pipeline around them, so every project writes, runs, and reports tests the same way.

Context
Several test projects at PERURI (INA Digital), each with its own framework, its own reporting, and the same setup problems solved again each time.
My role
Built the two shared core libraries and the pipeline around them, so projects share one way to write, run, and report tests.
Decisions and trade-offs
First, one shared core instead of a framework per project — it costs upfront build time and every project upgrades together, but it stops the same setup problems being solved many times. Second, release the cores as versioned packages from main, so a project can stay on a version that works and upgrade deliberately instead of drifting on its own copy.
How I verified it
Tests run in the pipeline on every deployment through Jenkins quality gates, with Allure reports and notifications to the team. Coverage and execution are tracked in the QA Test Management System, and automated tests cover 99% of critical user journeys.
  1. Versioned package

    Build on a shared core

    API Test Core (Java 17, RestAssured, Cucumber) and Web Test Core (TypeScript, Playwright, Cucumber) provide authentication, request and assertion steps, schema validation, multi-environment config, and test data from Google Sheets. Each merge to main publishes a new version.

  2. Running

    Run in the pipeline

    A Jenkins shared library runs the tests, stores the Allure report, and notifies the team in Google Chat.

  3. Ready for review

    Review the results

    Teams see which checks passed or failed and track coverage and execution in a QA Test Management System built on Google Sheets.

Outcome: 99% of critical user journeys automated with one framework for web, mobile, and API.

AI-assisted testing · Human review

AI Agent Speed: test triage with a person in the loop

When an automated test fails, someone has to work out whether the product, the test, the test data, or the environment broke. At PERURI (INA Digital) I'm building AI Agent Speed, an agent workflow that gathers evidence first and stops for a reviewer before changing what counts as a pass.

My role
Designing and building AI Agent Speed: the agent workflow, its evidence-first steps, and the review gates that stop it changing what counts as a pass.
Decisions and trade-offs
First, the agent gathers evidence before it guesses, and it may only restore test data, rerun, or propose a repair — it never changes what counts as a pass on its own. That costs reviewer time on every borderline case, but it keeps a wrong repair from silently passing a broken product. Second, verify locally before claiming anything live: four local suites with controlled inputs, and live accuracy left unmeasured rather than guessed.
How I verified it
See “What has been verified so far” below: synthetic replay (illustrative only), 44/44 local workflow checks, and live model evaluation not measured yet.
  1. 01

    Collect evidence

    Read the trace, logs, and request ID before guessing. An API 500 sends it to the server logs for that request.

  2. 02

    Classify the failure

    Decide whether the product, the test, the test data, or the environment is the likely cause.

  3. 03

    Act within limits

    Restore test data and rerun, or propose a repair such as updating how the test finds a renamed button. The original checks stay in place.

  4. 04

    Stop for review

    A change to what counts as a passing result waits for a reviewer. Without enough evidence, the agent escalates instead of assigning a cause.
